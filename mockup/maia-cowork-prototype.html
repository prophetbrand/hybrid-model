MAIA Cowork

DecideDelivery model: same image, our config, our extensionsHow we get every Lyzr update while keeping the white label and our own enhancements. No skinning, no fork.

Layer 1, white label is config. Product name, logo, colour tokens, fonts, feature flags (no Beta badge, no Tweaks), model options, and a list of custom sidebar and Help links, all in a tenant config Lyzr reads. Prophet edits config, never CSS. If Cowork has no tenant config today, that is the first ask.

Layer 2, enhancements go upstream as generic features behind flags. Multi-file skills, GitHub skill sync, request-access tiers, custom links, embedded apps in Agents Hub. Prophet specs them, Lyzr builds them into the product, Prophet turns the flag on. One codebase, parity by construction.

Layer 3, Prophet-specific pieces live outside Cowork behind standard interfaces. MCP servers, skills repo, design system, Azure SSO via OIDC, usage events to Snowflake. Cowork supports the interface; Prophet owns what is on the other end.

Deployment. Lyzr ships a versioned container image or Helm chart, the same one behind their SaaS. Prophet runs it in AWS with its config mounted. Upgrade = bump version + 15-minute smoke checklist (SSO, sidebar links, MCP connect, a skill runs, link-out opens). Monthly cadence, N-1 supported.

Contract points.

  • No Prophet-specific code in Lyzr's repo and no Lyzr patches in ours. Everything Prophet needs is config, a flag, or an interface.
  • Config schema is stable or versioned, so an upgrade cannot silently drop our links or branding.
  • A shared backlog for Layer 2 asks, with what ships in which release.

Why not skin their UI. CSS overrides break the moment they rename a class or move the sidebar. Config-driven theming survives a refactor; overrides don't.

Ask LyzrEmbed Architect apps inside Cowork ("Open app")New tab or embedded? Decides whether app use stays inside the Cowork experience.

Where it shows up. Agents Hub lists Architect apps (Presentation Studio, Market Sizing) with an "Open app" button. In the MAIA Agent Library today that button launches the app on its own URL in a new tab.

Why it matters. The session set a goal of not pushing people to too many clicks outside Cowork. A new tab means leaving Cowork, an SSO bounce through Keycloak, and a separate window of work. Embedding keeps people in one place but raises its own problems.

What embedding needs. Architect apps gate on Keycloak through SSOGuard. An embedded app has to accept the Cowork session as the user's identity, or the user logs in again inside the frame. Iframes also run into third-party cookie rules and the app's own frame-ancestors policy.

Questions to ask Lyzr.

  • Can Cowork embed an external web app at all (iframe, side panel, or artifact-style pane)?
  • If yes, can it pass the signed-in user's identity to the app, or does the app re-authenticate?
  • If no, can "Open app" at least open in a new tab with SSO already satisfied, so there is no login prompt?

Fallback if the answer is no. Keep "Open app" as a new tab, make sure Keycloak and Azure sessions are shared so it opens without a prompt, and accept that apps live beside Cowork rather than inside it.

Ask LyzrRequest-access flow for restricted agents and skillsMAIA has endorsed / restricted / private with an approval step. Cowork has Mine / Shared / Company.

Decision so far. Prophet keeps control of endorsed agents and of who gets restricted ones. That tiering has to exist in Agents Hub and Skills, not only in the old Agent Library.

What Cowork has today. Tabs for Mine, Shared with me and Company, plus Private and Built-in badges on skills. There is no restricted tier and no "Request access" action.

To ask. Can a Company agent be marked restricted, with a request that routes to an approver, and can the same tiering apply to skills? Who in Prophet is the approver, and where do they see requests?

Ask LyzrMulti-file skills and GitHub sync for skillsCowork takes one markdown file per skill. Prophet skills are folders in GitHub.

What we found in testing. The Skills page only accepts a single markdown upload. Skills with supporting files, scripts, references or templates cannot be loaded as they are, so they get flattened or trimmed by hand.

Why it matters. The diagram draws "Skills and MCP" as a live flow from GitHub into MAIA Cowork. Today that flow is a person copying markdown into the Skills page. When a skill changes in GitHub nobody updates the Cowork copy, and there is no way to tell which version a consultant is running. The skills repo is the thing that makes Prophet's work distinctive, so this is where drift hurts most.

What we would ask for.

  • Multi-file skills: a folder or zip with SKILL.md plus supporting files, matching the Claude skill format Prophet already uses.
  • GitHub sync: point Company skills at a repo and branch, so a merge updates the skill in Cowork, with the version shown on the card.
  • A "Prophet endorsed" tab or badge driven by that repo, so endorsed skills are the synced ones and personal uploads stay separate.

Fallback if the answer is no. Keep a script in the skills repo that flattens each skill to one markdown file and a checklist for re-uploading on release. Slower, but at least versioned.

DecideMigration plan from today's MAIA to the hybrid modelClient MAIA stays on the existing platform and gets re-linked. Internal MAIA retires into Cowork. Nobody has sequenced it yet.

See the full proposal: Backwards compatibility plan →

Decision so far. Client MAIA is the existing MAIA platform, not a Cowork tenant. Clients keep the agent library they have today; Cowork links out to it from the bottom-left.

What moves. Internal users: intranet link, General Chat history, favourites, feedback submissions, endorsed and restricted agents, Ask MAIA. Admin tools: UI Configuration, Dashboard and Eval Console live in the internal MAIA that goes away. Client orgs: untouched, but the Prophet strategists inside them now arrive from Cowork via SSO.

To decide.

  • Cutover order: Cowork live for a pilot group first, or everyone at once with internal MAIA left read-only for a period?
  • Where the admin tools go when internal MAIA retires: keep a Prophet-only admin org on the MAIA platform, or ask Lyzr for equivalents in Cowork.
  • Which existing agents are re-pointed into Agents Hub, which stay client-only, and which are dropped.
  • Who tells users what to use during the overlap, and what the intranet link points at on day one.
DecideConnector list and tool-approval policy (Foundry + IT)Cowork runs connectors as the user, with their permissions, and offers "Automatically approve". Foundry and IT define what is allowed.

Owner. Foundry and IT together.

To define. Which connectors are enabled at company level (Microsoft 365 and SharePoint are the likely first; GitHub for builders only?); whether "Automatically approve" is available to everyone, to power users, or locked to manual by admin policy; which actions are always-ask regardless of mode (send email, delete, push to main); a security review of Cowork's tool-use model, since the existing pen-test covered an app with no agents behind it.

To ask Lyzr. Can admin policy pin the approval mode and set always-ask actions per connector, and are tool calls logged in a way IT can export?

Client MAIA (existing platform)

Ask LyzrBake UI Configuration into client suborg creationUI Configuration is only used for client sites. Branding and screen visibility could be part of creating the suborg instead of a separate admin page.

Today. UI Configuration is a page in internal MAIA: per session you pick a client name and logo and toggle Home, General Chat, Agent Library, Accelerator Network, Help and Dashboard, then publish. Internal MAIA is going away, so the page needs a new home or needs to disappear.

Proposal. Make it a step of "Create client suborg": name, logo, which screens are on, who the Prophet admins are. One place, no separate publish step, nothing left behind in an internal MAIA that no longer exists.

To ask Lyzr. Can suborg creation take branding and screen visibility as inputs, and can a Prophet admin edit them later from inside the client org rather than from a separate console?

DecideRetire the Dashboard; Eval Console is unprovenDashboard (support, feedback, review requests) is replaced by Snowflake. Eval Console is net new and untested.

Dashboard. Decommission. Feedback and review requests become events in Snowflake alongside usage. Needs a replacement for the "Send feedback" action itself (in Cowork it sits in Help & Info) and somewhere for a reviewer to see requests, even if that is a Snowflake view.

Eval Console. Net new, not yet used. Decide whether it is worth keeping on the MAIA platform as an admin-only tool, or whether grading Cowork answers moves to a script that writes results to Snowflake.

Ask LyzrConfirm "computed, not stored" for Lyzr API in writingLyzr API runs outside Prophet's AWS. The position is that client data is processed there but never stored. That needs to be true of logs, traces and upstream model providers too.

Decision so far. Acceptable for client data to be computed on Lyzr's servers because nothing is stored. The "client material in our AWS" principle covers storage, not processing.

To confirm with Lyzr. Request and response logging and how long it is kept; tracing or evaluation captures; whether prompts reach Anthropic, Google or OpenAI with zero-retention terms; region where Lyzr API runs; what the pen-test covered for apps that do have agents behind them.

Why. This is the sentence a client will ask Prophet to put in a contract: "Your data does not leave Prophet's environment except for transient processing, and is not retained."

Snowflake and data

DecideClient data goes only into its own warehousePer-client Snowflake databases, membership-gated, instead of a blanket ban. Replaces the earlier 'never enters Snowflake' rule.

Why it matters. Client material is covered by client agreements and by the rule that it stays per client. If it lands in Snowflake or the knowledge graph it can surface in another team's answer, and both stores fall into pen-test and audit scope for client data.

Proposal.

  • A written rule: client data only enters its own warehouse, a per-client Snowflake database (CLIENT_LARKFIELD, CLIENT_NORTHWIND …), never the Prophet warehouse or the knowledge graph.
  • Access through the Client warehouse MCP only: gated on membership of that client's org or the Architect app running for that client, one credential per client in AWS Secrets Manager. Prophet-wide roles do not grant access.
  • Architect apps can still query client systems at run time; cw.sync is the only path that copies data, and only into that client's warehouse.

What to decide. Who enforces the rule, and how we audit that it holds.

DecidePer-user access or one service account for Snowflake and the knowledge graphCowork runs as the user. The MCP servers may not.

Decision so far. Prophet owns the MCP servers. Identity is not settled, but IT will most likely route it through the existing Keycloak and Azure setup rather than anything new.

Risk. If the MCP servers connect with one service account, every user effectively sees everything that account can see, whatever their own access is.

What per-user needs. The user's identity has to pass from Azure through Cowork to the MCP server, and the MCP server has to query Snowflake and the knowledge graph as that user or apply their permissions itself.

What to decide. Per-user or service account for launch, and if a service account, what it is allowed to read and who signs off.

Ask ITSecurity review for Snowflake outside AWSSnowflake may live outside Prophet's AWS. IT asked how to orient around data security for it.

Network path. Calls go from Cowork and the MCP servers in Prophet's AWS to Snowflake. We need to know whether that path leaves AWS and over what.

Encryption and private link. Confirm encryption in transit and at rest, and whether a private link is available so traffic does not cross the public internet.

What IT needs from Foundry. A list of the MCP servers that connect, what each one reads, and how they authenticate.

Timing. The review needs to land before usage data from ClickHouse goes in, since that is first on IT's plan.

Backwards compatibility plan — MAIA → MAIA Cowork

Proposal, 21 Oct 2026. How existing Studio agents, Architect apps and chat sessions carry over, without knowing Cowork's schema or all of MAIA's implementation yet.

1. What we know and what we don't

Known

  • MAIA agents are Lyzr Studio agents: each has a stable Lyzr agent ID and runs on Lyzr API. MAIA's Agent Library is a catalogue over those IDs with Prophet metadata (endorsed / restricted / private, author, favourites, ratings, query counts, conversation starters).
  • Architect apps are Next.js web apps on their own URLs, gated by Keycloak SSO (SSOGuard), calling Lyzr API agents through the app's own /api/agent proxy. The library only stores a card and an "Open app" link.
  • Cowork's Agents Hub says it holds "agents you build, agents shared with you, and agents your company runs here or imports from elsewhere". "Imports from elsewhere" is the hook to test first.
  • Both sides authenticate through Azure, so a user's identity (email) is the same object in MAIA and Cowork. Ownership can map by email.
  • Cowork keeps chats, projects, artifacts and skills in its own store; its UI shows chats grouped by day with ids and timestamps, and projects with shared instructions and files.

Unknown (and who answers it)

  • Cowork's data model for agents, chats, projects, artifacts: fields, ids, whether there is an import API. (Lyzr)
  • Whether Agents Hub can reference an external Lyzr agent by ID without copying it. (Lyzr)
  • MAIA's chat storage: where General Chat conversations live, export format, attachment storage (S3 bucket seen: prophet-maia-chat-attachments). (Lyzr, with Foundry confirming)
  • Exact list of production agents, apps and owners after removing UAT test agents. (Foundry)

2. Principles

  • Reference, don't copy. Wherever Cowork can point at an existing Lyzr agent ID or app URL, do that. No rebuilds in phase 1.
  • Nothing is deleted on cutover. Internal MAIA stays up read-only for a defined window.
  • Identity maps by email. No manual re-assignment of ownership.
  • Each track has a cheapest option that works with zero Lyzr changes, and a better option that needs one.

6. Sequence and gates

  • Discovery (1–2 weeks): Lyzr answers the schema questions below; Foundry produces the inventory (agents, apps, owners, tiers, usage from Eval/Dashboard, chat volume).
  • Pilot (2 weeks): A1 or A2 with 5 agents, B1+B2 with 2 apps, C1 on, for a 10-person group. Gate: every pilot user can reach their agents and apps from Cowork without a login prompt.
  • Cutover: intranet link → Cowork; internal MAIA read-only; Ask MAIA rewritten; usage events flowing to Snowflake.
  • Close-out (90 days later): decide on C2/C3 from what pilot users actually missed; retire internal MAIA.

Rollback at any gate: flip the intranet link back; nothing has been deleted.

7. Questions for Lyzr that unblock this

  • Agents Hub: can a Company agent reference an existing Lyzr Studio agent by ID, and is there a bulk import? What fields does an agent object have (name, description, starters, tags, visibility, owner)?
  • Can an Agents Hub card be a launch link to an external app (Architect app) with an "Open app" action? Can Architect write that card as a deploy target?
  • Chat schema: what does a Cowork chat/message/attachment look like, is there an import API, and are chat ids stable across upgrades?
  • MAIA export: can MAIA conversations and attachments be exported per user, in what format?
  • Identity: is the user's email the stable key on both sides, so ownership maps without manual work?
  • What survives a Cowork upgrade: imported agents, cards, chats, config? (ties to the delivery model item)

Inside Prophet's AWS · Foundry

Prophet knowledge base — AWS Neptune + S3

The Prophet brain. Documents land in S3, the entity graph lives in AWS Neptune, and a passage index sits beside them for semantic search. Related by embeddings and ontology rather than hand-built tables. Snowflake feeds it structured entities; the Knowledge graph MCP serves it.

Sources and ingestionSharePoint → S3 → Neptune

SharePoint, past client decks, frameworks and points of view. Ingestion copies each file to S3, extracts text and entities into Neptune and the index, and carries the SharePoint ACL and client tag through so the MCP server can filter per user. Deleting a document means removing the S3 object and its graph node together.

Three parts, one brainS3 + Neptune + passage index

S3 is the document store: every ingested deck, doc and page as the source of truth, versioned, with its SharePoint ACL and client tag as object metadata. AWS Neptune holds the entity graph: clients, engagements, frameworks, people, documents and how they relate, with each document node pointing at its S3 object. Neptune is not a vector store, so a passage index (Neptune Analytics vector similarity, or OpenSearch / pgvector) sits beside it for semantic search. kg.search hits the index, kg.related walks Neptune, kg.get_document reads S3.

Inside Prophet's AWS · Foundry · hypothetical design

MCP servers (AWS) — the compute step

When a user asks Cowork something that needs Prophet context, the call goes to these servers. They check who is asking, read the knowledge graph or the right warehouse, and return an answer with its sources. Everything here is a proposal to react to, not a build.

A. Request flow

1User asks in Cowork"How many clients did we work with in 2025?"
2Cowork picks a toolFrom the MCP manifest, and sends the call with the user's token.
3Gateway checks identityValidates the token (Azure via Keycloak), resolves role and tenant.
4Server runs the toolKnowledge graph and Snowflake in parallel when both are needed.
5Result returnsWith sources and row counts; Cowork writes the answer.
6Call is loggedAs a usage event into Snowflake.

Knowledge graph MCPUnstructured Prophet knowledge: graph RAG over decks, documents and SharePoint

C. Cross-cutting

One skeleton, two data backendsShared where it is not about the data

The Snowflake and Knowledge graph servers are instances of the same base: the gateway (token, role, tenant), usage logging, guardrails, deployment and failure handling are shared, and both expose the same low-level contract: describe (what this user may see), query (run it, return rows plus the exact query that ran) and lineage (source and freshness). What differs is the query language underneath (SQL on Snowflake; openCypher or Gremlin on Neptune) and the task tools on top. The model writes good SQL and poor Gremlin, so on the graph the task tools (kg.search, kg.related, kg.timeline) are the main surface and raw kg.query sits behind an allow-list for Foundry and power users; on Snowflake sf.query with an allow-list does most of the work and sf.metric keeps governed numbers from being re-derived.

Neptune's own access control is coarse (IAM at cluster level), so per-user filtering by SharePoint permission is done by the server on the way out, from ACLs carried through at ingestion. That is a Foundry build item, not a store feature.

Identity and roles

Azure token → Keycloak → MCP gateway validates the JWT. Role claims map to Snowflake roles and knowledge graph filters. No shared service account. Power users (Claude) use the same path with a personal token.

Isolation

Three tiers of data: Prophet warehouse (shared, role-filtered); client warehouses (one database per client, membership-gated); knowledge graph (Prophet knowledge only; client decks tagged by client and filtered by membership). Cross-tier joins are refused by the gateway.

Logging and measurability

Every call writes tool, user, role, tenant, latency, rows and cost to a usage_events table in Snowflake. Cowork and Client MAIA chat events land in the same table. This is what replaces the old Dashboard.

Deployment

Code in GitHub, one repo per server. GitHub Actions builds containers; ECS Fargate in a private subnet; Snowflake over PrivateLink; secrets in Secrets Manager. Manifest published to Cowork at company level and to Claude for power users.

Guardrails

Read-only by default; row and time caps; SQL allow-list for sf.query; PII masking on finance and CRM columns; every answer carries its sources. cw.sync and ds.lint are the only tools that write anything.

Failure modes

Token invalid → 401 and Cowork says "sign in again". Warehouse timeout → partial answer with "Snowflake didn't respond", the knowledge-graph half still returned. Schema change in IT's Snowflake → sf.describe fails loudly and the Foundry owner is paged.
